# Issueテンプレートと情報選別規則

## 文書の役割と読み手

Issue本文は実装の実行契約であり、仕様書の複製や調査日誌ではない。
読み手は過去の議論に参加しておらず、解く問題、必要な結果、作業の境界、完了判定を本文から判断する実装担当者とする。

補足の詳細は仕様書へリンクする。
削ると実装判断または完了判定が変わる情報だけをIssueへ残す。

## プロジェクトテンプレートの優先

本文を作る前に、リポジトリのIssue form、Issueテンプレート、contribution規約、必須フィールドを確認する。
プロジェクトテンプレートがある場合は、その見出し、順序、フィールド、チェック項目を維持する。
選んだ情報をテンプレートへ配置し、下記の既定テンプレートを追加しない。

適用できるプロジェクトテンプレートがない場合だけ既定テンプレートを使う。
仕様書に該当情報がない任意セクションは省略し、中身のない文を作らない。

## 既定のIssue本文テンプレート

```markdown
## 解決したい問題

{現在の挙動または不足している機能と、それによって起きている具体的な問題。}

## 完了後の状態

{完了後に外部から確認できる状態を1文または2文で示す。}

## 現在の挙動

{現在システムが行う処理。新機能の場合は不足している経路または手作業を示す。}

## 期待する挙動

{何を契機に、どのコンポーネントが何を処理し、結果をどこへ保存または返却するか。}

## スコープ

### 対象

- {期待する挙動を提供するために必要な作業。}

### 対象外

- {近接しているが、このIssueでは扱わない責務。}

## 受入条件

- [ ] {完了後の状態を証明する観測可能な結果。}
- [ ] {守る必要がある失敗時または境界の挙動。}

## 設計を拘束する決定

- {実装担当者が維持する設計判断と、その判断を拘束する理由。}

## 未決事項

- {未決の選択、判断基準、決定者。}

## 仕様書

- [要件定義書](../blob/{BRANCH}/.specs/{FEATURE_DIR}/requirement.md)
- [設計書](../blob/{BRANCH}/.specs/{FEATURE_DIR}/design.md)
- [タスクリスト](../blob/{BRANCH}/.specs/{FEATURE_DIR}/tasks.md)
```

## 情報の選別手順

`requirement.md`、`design.md`、`tasks.md`を、そのまま転記するセクションではなく候補情報の出典として読む。
次の順序で情報を選ぶ。

1. 要件から解く問題と、外部から確認できる完了後の状態を特定する。
2. 実装判断を変える場合は、現在と期待する挙動を、主体、契機、処理、保存先または返却先まで具体化する。
3. 対象と対象外を分け、近接する作業が要件に見えないようにする。
4. 要件レベルの受入条件を、観測可能な挙動で検証できるチェック項目へ変換する。
5. 制約、互換性要件、セキュリティ境界、外部契約に反するため変更できない設計判断だけを理由付きで残す。
6. 実装担当者が安全に決められない未決事項だけを残し、判断基準と決定者を書く。
7. アーキテクチャの詳細、タスク分解、見積もり、背景の証拠は仕様書へリンクする。

主な機能の一覧、フェーズ別タスク、見積もり、技術スタック、調査履歴、仕様書の全注意事項を機械的に再掲しない。
実装方法または完了判定を変える場合だけ、その情報を残す。

## タイトル

プロジェクトのテンプレートまたはcontribution規約が別の形式を定めていなければ、`[Feature] {FEATURE_NAME}`を使う。

`FEATURE_NAME`は次の順序で決める。

1. `requirement.md`の最初の`# `見出しを読む。
2. `要件定義書`、`要件定義`、`仕様書`、`Requirements Document`、`Requirements`、`Specification`、`Spec`を取り除く。
3. 前後の空白を削る。

例:

- `# メンバー管理機能 要件定義書`は`[Feature] メンバー管理機能`になる。
- `# Authentication System Requirements`は`[Feature] Authentication System`になる。

## 出典の対応

仕様書は次の用途で使う。

- `requirement.md`: 解く問題、完了後の状態、現在と期待する挙動、作業範囲、受入条件
- `design.md`: 設計を拘束する決定、制約、互換性境界、未決の設計判断
- `tasks.md`: 実装の補足と追加の完了証拠。フェーズ構造やタスク見出しは既定では転記しない

仕様書に具体的な受入条件がない場合は、Issueを作る前に不足を報告する。
「テストが通る」「コードレビューが完了する」のような一般条件は機能の完了を証明しないため、代わりに補わない。

## GitHub Issueの作成

リポジトリで利用できるGitHubクライアントを使い、選んだタイトル、本文、ラベル、担当者でIssueを作成する。
信頼できない本文をshell展開せず、利用できる場合はファイルまたは同等のリテラル入力として渡す。

## Projectへの追加

`--project`が指定されている場合は、現在のリポジトリからownerを解決し、作成したIssue URLをそのProjectへ追加する。

## 仕様書リンクのブランチ

`{BRANCH}`は次の順序で決める。

1. `--branch`引数
2. `.specs/.config.yml`の`default-branch`
3. リポジトリのワークフロー規約
4. `main`
