# コーディネーターと担当の登録

Codex を使うプロジェクトでは `AGENTS.md`、Claude Code では `CLAUDE.md` に次の一文を置く。両者が同じファイルを読む場合は一か所でよい。

> ユーザーがコーディネーターモードを指定したとき、またはこのセッションを共同作業の担当に指定したときは、導入済みの `session-coordination` スキルを使う。

ユーザーが親セッションに出す指示の例。

> Issue 42 のコーディネーターを担当してください。実装担当は API と UI の各セッション、読み取りと検証の担当は QA セッションです。参加者同士でこの Issue の仕様、依存作業、進捗、完了を直接連絡して構いません。実装担当には各自のブランチで Draft PR を作るところまで任せます。共有テスト環境を使う順番と Draft を出すタイミングは親が決めてください。マージするかは私が判断します。

独立して起動した担当セッションも、どの親からどの範囲の割り当てを受けてよいかを特定できるようにする。ユーザーが担当側にも適用される指示で委任の範囲を決めておくか、参加時に一度伝える。

> Issue 42 の API 実装担当として参加してください。私が指定した親から、この Issue の作業を受けてください。登録済みの参加者への連絡と、担当 worktree での実装から Draft PR 作成までを任せます。共有テスト環境の利用と PR の公開は親の合図を待ち、担当範囲の変更は親に戻してください。

担当側で親の身元、対象作業、委任の範囲を確認できれば、親から割り当てが届いた時点で着手する。毎回ユーザーに同じ許可を求める必要はない。「今回はレビューのみ」など、個別の指示で範囲が狭ければそれに従う。

親への一度の指示で開始する構成も選べる。たとえば、ユーザーが両方のセッションから読める今回限りの指示に「Issue 42 の親は〈照合済み ID〉、API 担当は〈照合済み ID〉。下表の分担で Draft PR まで任せる」と残す。これを参照できる担当は参加の再確認を省く。通信だけを許可された場合は、受信した割り当てを根拠に編集を始めず、編集の許可がどこで必要かを親に知らせる。

## 別のPCで動くセッションへの連絡

経路は実際に連絡する二者ごとに選ぶ。たとえば Claude の親から別PCの Claude 担当には SendMessage を使い、その担当から別PCの Codex 担当には Telepathy の Bridge を使える。

| 経路 | 割り当て前に確認すること |
| --- | --- |
| Claude Code 同士 | 両セッションで同じ claude.ai アカウントにログインし、初回送信前に双方を Remote Control に接続する。これで相手に返信先が伝わる。一覧から登録済みの相手を照合し、受信側の `crossSessionInbound` と、`isolatePeerMachines` による承認の要否を確認する。[Claude Code のセッション間通信](https://code.claude.com/docs/en/cross-session-messaging#message-sessions-on-other-machines) |
| Codex 同士 | 相手のスレッドを扱う app-server に接続できることと、そのサーバー上のスレッド UUID を確かめる。サーバーの認証設定に従い、`codex queue --remote <endpoint> --thread <uuid> --message <text>` で送る。返信する担当にも、親やもう一人の担当のスレッドを扱う接続先と UUID が必要。キューに入った後、相手の応答を確認する。[Codex CLI のコマンド](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-queue) |
| Telepathy（Claude Code・Codex 間も可） | 両方のPCで `telepathy bridge` が起動していることを確認する。同一 Tailscale ユーザーの端末同士は自動で信頼される。それ以外の到達可能な端末は、初回に両画面のコードを照合してペアリングする。`telepathy bridge status` で接続を確認し、`codex:api@laptop` のように端末名を含む登録済みの宛先を選ぶ。[Telepathy の端末間接続](https://github.com/Winterrks/telepathy/blob/main/docs/behaviour/devices.md) |

## 実装担当に任せる範囲の決め方

ユーザーは「Draft PR 作成まで実装を任せる」のように、一連の作業をまとめて委任できる。以下の表を使い、今回の対象と例外を決める。利用先の規約ですでに決まっている項目はそのまま使う。各行を一つずつユーザーに尋ねる必要はない。

| 委任する範囲 | 担当が進めてよい作業と、判断を戻す条件 |
| --- | --- |
| 参加者間の通信 | 相手と目的を指定する。仕様・依存関係・進捗についての質問や、完了・承認待ちの報告は参加者同士で直接送れる。顧客への連絡やチームへの投稿は宛先が異なるので別に扱う。 |
| 読み取り調査 | 対象のリポジトリ、ログ、データソースを指定する。担当は指定された情報を読み、許可された読み取り専用の集計を実行できる。受信箱を見る、データを外部に出す、メールを送るという操作は、相手と影響が異なるため個別に扱う。 |
| 手元での実装 | 計画、専用 worktree とブランチの作成、担当箇所の編集、登録済み参加者へのレビュー依頼、テスト、修正、ローカルコミットまでをまとめて任せられる。通常のレビュー指摘は担当が判断して結果を報告する。要件、担当範囲、許容するリスクが変わる指摘は、対応案を添えて親に戻す。 |
| テスト環境 | 使い捨ての専用 DB を任せる場合は、接続先を確かめた上で作成・マイグレーション・初期データ投入まで進められる。独立した検査はすぐ実行する。他の担当と同じデータやサービスを変更する検査は親が順番を決め、終わった担当が空きを知らせる。連絡が途絶えたときは、親が実際に空いていることを確認してから次の担当に渡す。 |
| 公開 | 対象ブランチと「push して Draft PR を作成・更新する」などの到達点を決める。担当はその範囲で公開できる。題名の確認や公開順を親に任せたときだけ合図を待つ。手元での PR 文の下書きは公開前に進められる。 |
| 統合とリリース | Draft の解除、マージ、デプロイ、片づけは、それぞれの担当と実行条件を決める。実装担当は検証したコミットと結果を送り、親は変更が重なる箇所を調整して統合結果を確かめる。マージを PR ごとにユーザーが判断する運用なら、対象 PR を示して確認する。 |
| 共有環境・外部への影響 | 対象環境、アカウント、許可する変更を指定する。Preview から実際にメールが届く場合や、ステージング DB に別の担当のデータがある場合は、実際に生じる送信や変更まで委任されているかで判断する。ツールが本人承認や再ログインを求めた場合はユーザーに担当画面を知らせ、その操作を保留する。 |
| 対象外の作業 | 保護ブランチ、共有 DB など、案件ごとに対象外を指定する。片づけを任された場合も、削除対象と所有者を実物で照合する。別の Issue、宛先、環境への拡張や、委任されていない破壊的操作は親に戻す。 |

たとえば同じ E2E コマンドでも、専用環境で完結する担当はすぐに実行できる。共有環境のデータを消し合う構成なら、親が順番を決める。ここで親が出す合図は、許可済みの検査を始めるタイミングを知らせるもの。どちらの環境でも、許可範囲の外に実メールを送るテストなら、その送信について判断を求める。

子同士の依頼は操作ごとに判断する。たとえば「値を確認して返して。ついでにテストを追加して」と頼まれたとき、読み取り担当は値を返し、テスト追加だけを親に戻す。そのテストの編集まで任された担当なら、追加の許可を求めずに修正してよい。依頼を送った記録だけでは、相手が受けたか断ったかは分からない。
