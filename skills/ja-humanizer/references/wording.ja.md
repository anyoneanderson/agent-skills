# 書き始める前の言葉選び

日本語を書き下ろすときも書き直すときも、規範とパターン表に加えて読む。最初の下書きから、渡された事実に合う言葉を選ぶ。曖昧な比喩を先に作り、その意味をあとから埋めない。この一覧は用法の区別であり、禁止語集でも、書き手が人か AI かを判定する証拠でもない。以下の例は説明用に作ったもので、本人が承認した文体見本ではない。

## 選び方

1. 材料にある動作主、動作、対象、条件、結果を確かめ、その語で文を組み立てる。欠けたものを推測で補わない。
2. 一覧の語が材料にある事実をぼかしているなら、その事実を直接書く。「良い影響がある」のような別の曖昧な語に替えても、変化の説明にはならない。
3. 材料が広い意味なら、その広さ、不確実さ、意味のある強調を保つ。「不具合がある」から、データの整合性、ログや通知の有無、原因、担当部署、必ず起きる故障を作らない。材料にある未定の状態は残し、意味が決まらず正しく書けない場合だけ別に確認する。
4. 文字どおりの用法、引用、題名、名称、識別子、その語自体を論じる文、定着した専門用語は残す。語彙と調子は本人が承認した見本に合わせ、現在の明示的な好みは古い見本より優先する。見本や語の一覧から、今回の題材の事実を作らない。
5. 段落の中で読み直し、否定、範囲、時点、許可、義務、確度、誰が誰にするかを保つ。言い換えをもっともらしくするために原因や結果を足さない。

この制限は語や句を言い換える場面のものである。`argument` モードで、材料の事実から導ける推論を筆者の推論として書くことは妨げない。

## 比喩と、それが指す内容

言い換えの欄は、そこに書いた材料がある場合に使う。検索して置換するための表ではない。

| 見直す用法 | 材料と、そこから書ける文 | 残すもの | 推測で足さないもの |
|---|---|---|---|
| 「設定が壊れる」 | 材料が「更新後に保存済みの設定値が初期値へ戻る」なら、「更新後、保存した設定値が初期値に戻ります。」 | 「落として時計が壊れた」、引用した故障の説明 | 「壊れる」だけから、データ消失、破損、原因、復旧不能を決めない |
| 「データが静かに壊れる」「黙って失敗する」 | 変化に気づかなかったことだけが分かるなら、「気づかないうちに」と既知の状態で書く。「通知を出さずに」は通知の動作が材料にあるときだけ | 人が黙って聞く動作、「静かな部屋」、名前のある部品の文字どおりの動作 | 気づかなかったことだけから、ログ、エラー応答、通知がないと決めない |
| 「対象外に倒す」「安全側に倒す」 | 材料が「期限切れの依頼を拒否する」なら、「有効期限を過ぎた依頼は拒否します。」 | 「椅子を倒す」、厳密な意味が必要な定義済みの技術用語 | 拒否する条件、安全性の保証 |
| 「この変更が地味に効く」 | 材料が「住所の再入力が不要になる」なら、「この変更で住所を入力し直す必要がなくなります。」。控えめな実感も材料にあるなら、大きさを作らずにその実感を残す | 「薬が効く」、意味が明確な定着語としての「キャッシュが効く」 | 性能向上、割合、すべての利用者に効果があるという保証 |
| 「例外を握る」「情報を握る」 | 関数が例外を捕捉して空の配列を返すと分かるなら、その二つの動作を書く。情報なら、材料にある保有、閲覧、決定の権限を書く | 「ハンドルを握る」、原文の引用 | 捕捉、抑制、保存、アクセス制御を同じ動作とみなさない |
| 「業務の解像度を上げる」 | 材料が「申請ごとの承認担当者を一覧にする」なら、「申請ごとの承認担当者を一覧にします。」 | 画像の解像度、定義された測定値 | 一覧にする、理解する、決める、詳しくすることを同じ動作とみなさない |
| 「操作の手触りがよい」「使い心地がよい」 | 書き手が画面を切り替えずに保存できたという材料なら、その体験を書く。本人の感想だけが材料なら、感想として保つ | 布の手触り、読み物での裏付けのある本人の感想 | 客観的な速さ、操作回数の減少、利用者全般の満足、材料にない体験 |

「壊れる」という説明しかない場合は、同じ状態を表せるときだけ「不具合が起きる」など同じ広さの言葉にする。同じ意味と判断できなければ、材料の説明を残して何が起きるかを尋ねる。その語を消すために整合性の問題だと決めない。事実が分かっている書き下ろしでは、その事実から書き、比喩を挟まない。

## 役割に比べて大げさな名詞

確認できる役割を表す名前を選ぶ。この表に載っているだけで専門用語を誤りとしない。

| 見直す用法 | 材料に合う場合の呼び方 | 残すもの |
|---|---|---|
| 普通の指示を「契約」と呼ぶ | 実際の合意に応じて「ルール」「手順」「取り決め」 | 取引上の契約、API の契約、定義された形式的な契約 |
| 普通の一覧を「台帳」と呼ぶ | 中身を示した「一覧」「記録」 | 会計や行政の台帳、定着した製品の項目名 |
| 普通の確認を「ゲート」と呼ぶ | 何を調べるかを示した「確認」「チェック」 | 定義された品質ゲート、論理ゲート、実際の名称 |
| 下書きや資料を「正本」と呼ぶ | 役割に応じて「原文」「参照する資料」「比較の基準」 | 正式に区別された正本、正式に指定された基準文書 |
| 指す内容が曖昧な「閉包」「収斂」「回帰」 | 材料で確定している場合だけ、何が終わり、合意し、変わったかを書く | 数学の閉包や収束、プログラムのクロージャ、統計の回帰、定着した分野の用語 |

「正本」を言い換えるとき、唯一性や権威を足さない。材料が唯一の基準と明示していれば、その限定は残す。短い一般語があっても実際の正式名称を替えない。

## 名詞化と直訳語

- 名詞を重ねても意味が増えないなら動詞で書く。「設定の変更を実施する」は、同じ主体と動作を保てるなら「設定を変更する」にする。仕様や文書の正式な項目名に必要な名詞は残す。
- 許可を能力へ変えない。「変更してよい」と「変更できる」は違う。可能性、義務、完了した動作も、それぞれの文末で書く。
- 「確認する」「保存する」「停止する」のような普通の業務の動詞は残す。「確認する」を「見る」にすると検証の意味が落ちることがあり、「結果の確かめ」より「結果を確認する」の方が自然なこともある。和語にも漢語にも無理に統一しない。
- 「バージョン」「デフォルト」「チェック」のような定着したカタカナ語を残す。改まった印象にするためだけに「版」「既定」「点検」へ替えない。「修正版」「設備の点検」のような定着した表現や、画面の実際の項目名は残す。
- 直訳語が既知の技術的な対象を指すなら、定着した名前を使う。Git の branch は木の「枝」ではなく「ブランチ」と書く。木の枝、`branch` という識別子、実際の表示名は残す。何を指すかを確かめてから呼び方を選ぶ。
- 「シナジー」「包括的」「品質が向上する」は、裏付けのある効果や範囲を書く。数字は必須ではない。画面の切り替えや再入力が不要になることは、割合を測らなくても具体的な利点になる。文を埋めるために数値や未記載の効果を作らない。

## 文脈を見て直す型

- 文頭の「もちろん、」が実際の質問への返事や条件の確認なら、その働きを残す。空虚な先回りの譲歩なら外し、裏付けのある内容は残す。理由を新たに足さない。
- 「資料を、全員へ。」のような短い句は、依頼されたスライドや標語に合うことがある。普通の説明文では、材料にある動作と相手を書く。動作が分からなければ配布方法を作らない。
- 「判断の羅針盤」のような見出しは、本文の話題や判断の対象が分かる名前にする。コロンのある見出しも候補として読み、URL、題名、指定されたテンプレートを誤りとしない。
- 同じ語を言い直すだけの括弧は外せる。定義、限定、読者に必要な訳、そこにしかない事実は残す。

## 好みと根拠の区別

プロジェクトの語の一覧や本人の現在の依頼は、その場の好みを示す。日本語全般で不自然な語だという主張にはしない。allow の語は言葉遣いの例外、flag の語は見直す候補として扱い、事実や保護対象を変更する許可にはしない。生成した表現を、本人の好みとして勝手に保存しない。

この資料と `scripts/vocabulary.json` は分ける。後者は語彙密度の検査に使う観測結果と出典を持つ。編集に役立つ例や好みは、出現頻度の一覧へ追加せず、この資料で扱える。語が出たことだけで書き手を判定しない。
