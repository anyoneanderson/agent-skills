# AI の日本語の癖（等級付きパターン表）

ja-humanizer が書き直しと検査で使うパターンの正本。等級は「一つ見つけたときにどう扱うか」を決める。

- 第1級: 一つ見つけたら直す。書き手が自分の文でも毎回直しているもの。
- 第2級: 日本語の AI 文に特有の強い指紋。一つでも直してよいが、書き手の見本にその型があれば残す。
- 第3級: 単独では直さない。同じ段落に第1級か第2級が重なったときだけ直す。

各パターンは、見つけ方、直し方、例の順で書く。例の before は AI の下書き、after は書き手の手による書き直しから取っている。

## 第1級（一つ見つけたら直す）

### 中身の薄い文

見つけ方: 「削減」「向上」「改善」「柔軟」「迅速」のような評価語で項目が終わり、何が不要になるのか、以前はどうだったのか、なぜそうなるのかが書かれていない。読み手が次の行動を決めるのに要る事実（何をしたか、どれのことか、なぜそうなるか、誰がどこでやるか、いつ終わるか）が無い。

直し方: スキルは事実を足さない。欠けている事実を問いにして書き手に返し、答えが来てから書き直す。答えが無ければ、評価語だけの文は削る。

例:

- before: 「迅速なセットアップ: 複雑なハードウェアの導入が不要なため、短期間でシステムを立ち上げることができます。」
- 問い: 「不要になるものは具体的に何ですか（電源、回線、専用ソフトなど）。」
- after: 「早期導入: 電源や WIFI、専用ソフトのインストールなどは不要で、スマホにアプリをインストールするだけで短期間でサービスを立ち上げることができます。」

### 比喩動詞と硬い述語

見つけ方: 実際の処理を言わずに済ませる動詞。比喩動詞は「閉じる」「配る」「動く」「切り替わる」「揃う」「効く」「刺さる」「乗る」「噛ませる」「倒す」。硬い述語は「実現する」「可能にする」「提供する」「機能する」「担う」「果たす」「寄与する」「担保する」「整備する」「明確化する」。動詞の名詞化（「〜の向上」「〜の実現」「〜の可視化」）も同じ。

直し方: 誰が、何を、どうするかを書いた動詞に置き換える。「停止する」「許可する」「送信する」「保存する」「比較する」「拒否する」のように、プログラムや人が実際に行う動作にする。

例:

- before: 「モデル全体を閉じるのではなく高度なサイバー能力の部分だけを審査付きで配る設計です。」
- after: 「モデルの利用全体を停止するのではなく、サイバー能力のあるモデルのみを限定公開として審査制で利用を許可する。」

### 演出と脅しの締め

見つけ方: 事実を足さずに重みだけ足す語と、結果で脅す締め。「静かに」「同じ週に」「最重要」「賢さではなく時間差」のような対比、「この数字がないと判断できません」「〜しなければ手遅れになります」のような脅し。

直し方: 重み付けの語を削り、事実だけを残す。脅しの締めは、読み手が置くべき前提の提示に変える。

例:

- before: 「最重要システムで、脆弱性の公表から適用完了までに実際に何日かかっているかを、感覚ではなく直近の実績値で測ります。この数字がないと、猶予が縮んだときの危険度を判断できません。」
- after: 「利用しているシステムで脆弱性の発表から実際のパッチ適用まで何日かかっているかの実績を可視化してください。この実績値が AI セキュリティ時代では縮むことを前提に考える必要があります。」

### クッション言葉

見つけ方: 断り、抗議、依頼の前後に付く、内容の無い緩和。「ご理解いただけますと幸いです」「大変恐縮ですが」「お手数をおかけしますが」「差し支えなければ」の連続。悪い知らせを段落の後ろへ送る構成。

直し方: 結論を先に短く言い切り、感情や確度は一文で直接添える。措置は自分の行動として書き、理由を一文だけ付ける。

例:

- before: 「大変恐縮ですが、諸般の事情により、今回のご提案については一旦保留とさせていただければと存じます。ご理解いただけますと幸いです。」
- after: 「今回の件を受けまして、入金をいただくまでは保留とさせていただきたいと思います。」

### 相手の返答に依存する依頼の連鎖

見つけ方: 「〜でしたら、〜をお願いできますでしょうか」のように、条件が相手の回答にかかっていて、返答を待ってから次の依頼が始まる形。往復が一回増える。

直し方: いま頼めることは全部いま頼む。条件が「直前の問いへの答えを待つためだけ」のもので、依頼自体は答えに関わらず有効なら、依頼を独立した段落にして無条件で頼み、条件は相手側の判断材料として別に書く。同意、承認、権限、有効期限のように、満たされなければ依頼してはいけない実行条件は保持する。「同意済みでしたら、個人情報の送信をお願いします」は直さない。

例:

- before: 「上記時間帯に実施いただいているようでしたら加盟店パスワードが起因しているため、決済代行会社様にも合わせて調査依頼をお願いできますでしょうか。」
- after: 「「XX03」エラーは加盟店パスワードに起因するエラーですので、パスワードが正しく設定されていないことが想定されます。（中略）また、決済代行会社様にも合わせて調査依頼を出していただければ幸いです。」

### 現象の言い換えでしかない原因

見つけ方: 原因欄の語彙が経緯欄とほぼ同じで、新しい事実が無い。「設定が適用されていないことが原因」は「登録できてしまった」の言い換えにすぎない。「要件を満たさない実装が根本原因」は不具合の定義そのもので、循環している。

直し方: いつ、誰が、何を知らずに、何をしたか、の時系列を問いにする。答えが来たら、機構として書く。

例:

- before: 「管理画面での設定が会員画面の登録時に適用されていないことが原因でした。」
- after: 「当初の要件定義には分類制御が無く、その後追加でご要望をいただきました。管理画面の担当者は本仕様を考慮して開発しましたが、フロント画面の担当者が本要件を考慮せず開発したことが原因です。」

### 一般語だけの対策

見つけ方: 再発防止策や改善策が「徹底」「こまめに」「共有」「意識」「強化」だけで構成され、原因のどの工程を塞ぐのかが書かれていない。

直し方: 原因に一対一で対応する工程を名指しする。工程が分からなければ問いにする。

例:

- before: 「要件定義書のこまめな更新、社内での要件共有を徹底することで再発を防止できると考えております。」
- after: 「要件変更に対する要件定義書の迅速な更新、及び仕様変更が発生した場合の社内エンジニアへの周知を徹底します。」

## 第2級（日本語固有の強い指紋）

一つでも直してよい。ただし書き手の文体見本に同じ型があれば残す。解説記事ではラベル+コロンの箇条書きを書き手自身が使うことがあり、その場合は第3級として扱う。

| パターン | 見つけ方 | 直し方 |
|---|---|---|
| ラベル+コロンの箇条書き | 「**速度:** 処理速度が向上」のように太字ラベルとコロンで始まる項目が並ぶ | ラベルが情報を持たないなら消して本文だけにする。持つなら文にする |
| 三つ組 | 理由は3つ、要点は3つ、決めることは3つ、と項目数が常に3 | 中身が要求する数にする。1つでも4つでもよい |
| することができます | 「変更することができます」 | 「変更できます」 |
| まとめ節と期待の締め | 本文を言い直す「まとめ」節、「〜が期待されます」「今後の展開が注目されます」「〜と言えるでしょう」で終わる | まとめ節は削り、最後の具体的な事実で終える |
| 定型の導入 | 「近年、〜が注目されています」「本記事では〜を解説します」「〜をご存じでしょうか」 | 導入を削り、要点から始める |
| 定型の評価語 | 「浮き彫りにしており」「重要な示唆を与えている」「注目に値する」「画期的な」「多面的な」「包括的な」 | 何が見えたか、なぜ注目したかを具体に書く |
| 空虚な副詞 | 「静かに」「確実に」「大きく」「本質的に」「シンプルに」「適切に」「柔軟に」「明確に」 | 削る。残す必要があれば数値か条件に置き換える |
| 主語の過剰明示 | 毎文が「このツールは」「この記事では」「私は」で始まる | 同じ主語が続くときは最初だけ書く |
| 語尾と文長の均一 | 「です」「ます」「できます」が3文以上続く。一文が40〜60字に揃う | 語尾を変え、長短を混ぜる。書き手の見本があればその分布に寄せる |
| 機械的な接続 | 「まず」「次に」「最後に」「そのうえで」「あわせて」「なお」が段落ごとに置かれる | 論理の関係を示す語だけ残し、順序を示すだけの語は削る |
| 対比による重み付け | 「A ではなく B」「A だけでなく B」で、A を誰も主張していない | 読み手が実際に持つ誤解を正すときだけ残し、それ以外は B を直接書く |
| 用語の翻訳調 | 「〜において」「〜の観点から」「〜という側面から」 | 削るか、具体的な条件に書き換える |
| 見出しをセリフにする | 「同じ週に、Google と Anthropic も同じ方向へ動いた」のように見出しが文になっている | 名詞句にする（「Google と Anthropic も同様の方針へ」） |

## 第3級（単独では直さない）

同じ段落に第1級か第2級のパターンが重なったときだけ直す。人が意図して使うことがあり、一つだけでは AI の証拠にならない。

| パターン | 備考 |
|---|---|
| 太字 | 初出の定義と、見落とすと判断が変わる事実には使ってよい。数ではなく「ラベル+コロン」の型で判定する |
| 箇条書きそのもの | 手順、選択肢、チェックリストには適切 |
| 番号付き見出し | 参照しやすさのために使うことがある |
| 「〜ですね」「〜かもしれない」 | 推量や語調の調整として自然な場合が多い |
| 一文が長い | 主語と因果が通っていれば直さない。文長は見本が規則に勝つ |
| 全角ダッシュが一つ | 二つ以上、または他の型と重なったときに直す |
| 「これにより」が一つ | 連続したときに直す |
| 丁寧語の均一 | メールでは相手との関係で決まる。見本があればそれに従う |

## 直さないとき

- 引用、タイトル、固有名詞、その語自体を論じている箇所では、パターン語があっても触らない。
- 書き手の文体見本にある型は、そのまま残す。見本は語彙、語尾、文長、読者への態度について規則より優先する。規範が優先するのは、意味か論理に関わる箇所（論証の構造、機構の無い原因、例が支えない主張、未定義の術語）だけ。
- 改善幅が小さい文は、言い回しだけ整える。もともと自然な文を、規則に合わせるために崩さない。
- コード、パス、コマンド、frontmatter、リンク先、表のセルの中は触らない。
- 事実、数値、固有名詞、出典は、元に無いものを足さない。足りなければ問いにする。

## 問いの型

問いは、答えが無いと正しく直せない箇所に限る。語彙と演出の修正を先に済ませ、残った「中身の薄い文」「現象の言い換えでしかない原因」「一般語だけの対策」「選択肢を並べたのに日数が無い依頼」について、次の5種から該当するものを返す。期限や数値が要るかは依頼の内容で決まり、型に当てはまるだけでは問わない。問いは呼び出した人の言語で書く。

| 欠落 | 問い |
|---|---|
| 何をしたか | 「この結論の前に、実際に何を確認しましたか。」 |
| どれのことか | 「『既存ロジック』はどの範囲を指しますか。いつから使っているものですか。」 |
| なぜそうなるか | 「なぜそうなるのか、仕組みを一文で教えてください。」 |
| 誰がどこでやるか | 「この確認は誰が、どの環境で行いますか。相手に頼むものはありますか。」 |
| いつ終わるか | 「見込みの日数か期限はありますか。相手が選ぶのに要ります。」 |

問いに答えが無い場合は、その文を削るか、評価語を外して事実だけを残す。推定で埋めない。
