# 文脈を読んで評価する

ja-humanizer を変更、評価するときに使う。検査スクリプトはパターンを探すものであり、PASS は文章の合格判定ではない。検査結果に加え、意味と書き手の文体を確認する。ここにある例を、評価時の文体見本へ入れない。

## 確認用の例

以下は評価のために作った入力であり、書き手の文体見本ではない。各文を読み物モードで点検させる。独立した評価者を使う場合は、応答を記録するまで期待する判断を見せない。

| 例 | 入力 | 期待する判断 |
|---|---|---|
| 一つの例から広げすぎた結論 | 「この例では、申込書に必要な添付書類の名前を書き足しました。文章を書く仕事の正体は、事実を足すことだったのです。」 | 一つの添削から文章全般へ話が広がったことを指摘する。具体的な修正内容は残し、結論は削るか範囲を狭める。検査スクリプトの PASS で解消したことにしない。 |
| 抽象的な結び | 「担当者が下書きの金額を見積書と照合します。この工程は、その境界を文章の作業に引くためのものです。」 | 照合する作業は残す。境界の意味も新たな作業も説明していない末尾の文は削る。 |
| 自然な語尾の連続 | 「私は申込書を確認します。次に、添付書類の名前を見ます。足りない書類があれば、申込者に連絡します。」 | 手順をそのまま残す。語尾の連続だけを理由に、文の断片、倒置、体言止めへ変えない。 |
| 必要な解釈 | 「書類名を追記した版では、確認の電話が5件から1件に減りました。この試行では、書類名の明記が確認の手間を減らした可能性があります。」 | 範囲と不確実性を保った解釈を残す。例の後の結論を一律に削ったり、一般的な因果の断定へ変えたりしない。 |

書き下ろしでは「申し込みには氏名とメールアドレスが必要」という事実だけを渡し、個人ブログの短い導入を頼む。体験談は渡さない。事実を説明するか、必要な場合だけ本人の経験を確認し、同僚に指摘された話や解決を発見した話を作らないことを確認する。

見本選定では、本人が部分的に添削した記事を渡し、本人が書いたと思われる箇所を選ばせる。候補を原文で引用し、推定であることを説明する必要がある。作者を証明できたと断定したり、候補を承認済みの見本として保存したりしない。別に用意した本人確認済みの長い文はそのまま残す。長さだけを欠点としない。

## 改修やモデルの比較

各回に同じ資料、読者、長さの指定、本人確認済みの抜粋を渡す。実際に使ったモデル名、適用された指示、スキルのリビジョンを記録する。スキル改修を比べるときはモデルを固定し、モデルを比べるときはスキルを固定する。両方を変えた結果から、モデルによる差を断定しない。

文体見本に含まれない複数の題材を使い、可能ならモデル名を伏せて本人が読む。資料に無い事実の追加、意味の欠落、嫌な言い回し、直しすぎ、許容できる原稿までの修正時間を、検査件数とは別に記録する。一つの例から「癖が無いモデル」「常に文章がうまいモデル」と結論づけない。比較していない場合、モデル変更は試す案として書き、測定済みの改善にしない。

## 記事の修正を評価する例

以下は推敲の評価に使う課題文であり、文体見本ではない。

課題: 次の入力を読み物モードで点検し、裏付けのある意味を残して直す。事実を創作しない。上記の本人確認済みの抜粋を、この試行の文体見本には使わない。独立した評価者には課題と入力だけを渡し、出力を記録してから評価基準と照合する。

```text
AI 臭を消す作業の実体は、言い回しの置き換えもですが、事実の追加という文章のコンテンツの補強をやる作業になります。

文体見本は語彙、語尾、文長、読み手への態度を決め、規範が勝つのは論証の構造や機構の無い原因のように、意味か論理が合わなくなる箇所だけにしています。
```

評価基準: 最初の主張は添削例が支える範囲に絞り、何の情報が足りないかを直接説明する。2番目は、どの言葉遣いを見本に合わせ、どの矛盾や説明不足を直すのかを述べる。以前 after と呼ばれていたことを理由に、この2文を保存しない。特定の正解文との一致や検出件数0件を合格条件にしない。

本人が「空振り」のような比喩を嫌う場合は、その書き手と文脈での好みとして扱う。日本語に存在しない語や、特定モデルが書いた証拠と一般化しない。意味が分かりにくい比喩は、語の一律検出を追加しなくても文脈を読んで指摘できる。
